# Libmem.NET 2.3.0 → 2.4.0 execution plan

## Scope and guardrails
- Repository: `CardResearchLab/Libmem.NET`; baseline: released `v2.2.1`.
- Supported: Windows x64/x86, .NET 8, native C++/CLI with pinned `rdbo/libmem` SHA `a07c9942bf1358dabcc83eb0cd072736c749d7f8`.
- Public API additions are allowed in minor releases; breaking changes require explicit review.
- Out of scope: ARM64, Linux, macOS, Harmony/Mono/Unity, game state, IPC, any application-specific abstractions.
- Never bump the native submodule casually. Native version sync is a separate ABI and license review; current upstream default commit has not advanced past the pinned revision as of 2026-10-08.

## 2.3.0 checkpoints
1. Native coverage: inventory the pinned `libmem.h` process, threads, modules, symbols, segments, memory, scan, assembly, and Hook/VMT families against `Libmem.NET` and `ProcessSession`. Distinguish internal cleanup functions from consumer-facing operations. Every uncovered call receives a rationale instead of blindly adding an API.
2. Memory: implement `ReadInt64`, `WriteInt64`, `ReadPointer`, `WritePointer`. Pointer width must be read from the session's target identity. Do not silently truncate values for x86.
3. Runtime regression: preserve scan final-candidate and address-overflow fixes, injection error mapping, ownership retry, target-exit behavior, and x64/x86 pointer round trips.
4. Deliverability: build Release x64/x86, run Smoke, ExternalProcess, Hook/VMT, Injector, Public API checker, consumer tests, package verification. Review generated XML docs and changelog.
5. Release 2.3.0 only after all gates are green. Publish GitHub Release and NuGet as distinct, verified steps.

## 2.4.0 checkpoints
1. Assembly: add safe read-only, instruction-aligned code inspection helpers on top of existing `CodeLength` + `ReadMemory`, with overflow/partial-read handling and no automatic patching.
2. Symbols: ergonomic `TryFindAddress` API for normal native bad-address misses, retaining existing `FindAddress` behavior. Validate foreign/stale module identities and missing names.
3. Hook: focus on tests and documentation for instruction alignment, source protection recovery, trampoline ownership, and native limitations. No automatic global hook registry; no custom machine-code relocation engine.
4. Samples: demonstrate `ProcessSession.Assembly`, `Symbols`, and guarded Hook lifecycle from a consumer project without binding a game framework.
5. Gate: Windows x64/x86 Release suites, API baseline/compatibility diff, runtime package and dual-arch NuGet consumer smoke, optional Debug diagnostics, release candidate audit.
6. Publish 2.4.0 only when the 2.3.0 release is independently complete and verified.

## Branching and merge discipline
- Each small feature + tests belongs in a reviewable PR. Merge only after Windows CI.
- Do not stack a release tag on an unmerged or failing PR.
- The `VERSION` file remains the last released version until the release candidate is explicitly prepared.
- No public version or NuGet publication is inferred from code being drafted or a PR being opened.
